# Day 07

## 受講者が実装する場所

- `day07/app.py` の `run_graph()`

## 目的

- LangGraphで状態遷移を持つ処理フローを実装できるようにする
- stateに途中結果を保持し、デバッグ/説明ができるようにする

## ゴール（完了条件）

- 分岐が最低2パターン発生する
- どの分岐に入ったかがログで分かる

## 機能要件

コマンド

- `python -m day07.app` で起動できること（モジュール名は固定）

必須オプション

- `--text`：ユーザー入力（文字列、必須）

任意オプション

- `--mode`：分類方式（`llm` / `rule`、デフォルト `rule`）

出力

- 正常時：標準出力に結果（文章）を出す
- 失敗時：標準エラーにエラーメッセージを出す

終了コード

- 正常終了：`0`
- 入力不備：`2`
- 実行失敗：`1`

受け入れ基準

- 入力に応じて分岐が最低2パターン発生する
- どの分岐に入ったかがログで分かる
- 分類不能時はデフォルト分岐へ入る（または明示的に失敗する）

## リサーチメモ（任意）

調べたURLや、理解した要点をメモしてください。

LangGraphの基本（state/node/edge、条件分岐）

State（バインダー）: システム全体で共有するデータ構造（型）。今回はAgentStateとしてinput, intent, output, errorsを定義し、各担当者が決められた欄にのみ書き込む決定論的なルールを敷いた。

Node（担当者）: 実際にバインダーへ書き込みを行う個別の関数。今回は分類、RAG、要約、フォールバックの各機能をカプセル化して配置した。

Edge（レール）: バインダーのintent欄を読み取り、物理的に次のノードへ受け渡すルーター。これにより「次に誰へ渡すか」をAIに考えさせず、Pythonコードによる完全な分岐制御を実現した。

AIエージェント開発におけるアーキテクチャ上の利点
生成（確率論）と制御（決定論）の完全分離（疎結合化）:
プロンプトでLLMに業務フロー全体を丸投げする手法から脱却。AIには「限定された専門タスク（Node）」のみを実行させ、全体の分岐やルーティングは強固なPythonの枠組み（Edge）で制御することで、ハルシネーションによるフローの崩壊を防ぐ。

「概念的な箱（モック）」でワークフローを先行構築する意義:
将来的にBedrock呼び出し等の予測不能で重たい本物のAI処理を組み込んだ際、AIが想定外の挙動を示してもシステム全体がクラッシュしないよう、あらかじめ絶対に脱線しない「頑丈な囲い（ベルトコンベア）」を構築してルーティングをテストしておくことが、エンタープライズ要求を満たす上で不可欠であると理解した。

将来の拡張性への担保:
この堅牢なワークフロー基盤（StateGraph）により、後続フェーズでのエラー自己修正ループ（Reflection）や、クリティカル処理前の人間による承認介入（Human-in-the-Loop）、状態の巻き戻しといった高度なBPM（ビジネスプロセス管理）機能の組み込みが容易になる。

## 付録：設計メモ

### 状態設計（state）

最低限、以下の情報をstateに持たせてください。

- `input`：ユーザー入力
- `intent`：分類結果
- `output`：最終出力
- `errors`：エラー情報（あれば）

### 分岐条件

以下のいずれかの方式で分岐してください。

- 方式A：LLMで分類して分岐（例：`rag` / `summarize` / `plan`）
- 方式B：ルールで分類して分岐（キーワード、正規表現など）

### 実装内容（例）

`day07/` 配下に、次のLangGraphを実装します。

- ノード1：入力を分類する（intentを決める）
- ノード2：intentに応じて処理を分岐する
  - 例：RAG（仮でもOK）/ 要約 / タスク分解
- ノード3：最終出力を整形する

最低限、分岐が2つ以上あること。
