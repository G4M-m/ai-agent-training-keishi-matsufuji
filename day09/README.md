# Day 09

## 受講者が実装する場所

- `day09/app.py` の `load_suite()`
- `day09/app.py` の `run_case()`

## 目的

- 最低限の評価（テスト入力セット）を作り、改善前後の差分を説明できるようにする

## ゴール（完了条件）

- テスト入力セットを `--suite` で実行できる
- 結果JSONを `--out` に出力できる

## 機能要件

コマンド

- `python -m day09.app` で起動できること（モジュール名は固定）

必須オプション

- `--suite`：テスト入力セットのパス（必須）

任意オプション

- `--out`：評価結果の出力パス（デフォルト `day09/result.json`）
- `--timeout-sec`：1ケースあたりのタイムアウト（整数、デフォルト `30`）

出力

- 正常時：標準出力にサマリ（成功/失敗件数）を出す
- 失敗時：標準エラーにエラーメッセージを出す

終了コード

- 正常終了：`0`
- 入力不備（`--suite` 不正など）：`2`
- 実行失敗：`1`

受け入れ基準

- `--suite` で指定したケースを順に実行できる（まだ中身はスタブでもよい）
- `--out` にJSONを出力する（成功/失敗の一覧を含める）

## 実装タスク

- `day09/app.py` の `load_suite()` と `run_case()` を実装し、機能要件を満たす
- テスト入力セットを作成し、実行結果を記録する

## テスト入力セット

- ケース一覧：

実装課題

- 最低5件の入力ケースを作る
`day09/suite.json` に5件定義
  1. `case1-normal`: 正常系（通常の要約指示）
  2. `case2-boundary-long`: 境界値（200文字を超える長文入力）
  3. `case3-invalid-empty`: 異常系（空文字入力）
  4. `case4-safety`: 異常系（プロンプトインジェクション攻撃）
  5. `case5-normal-rag`: 正常系（社内規定のRAG検索）

## 評価結果

- 成功/失敗の集計：
  - 改善前：成功3件 / 失敗2件（合計5件）
  - 改善後：成功5件 / 失敗0件（合計5件）
- 失敗の分類：
  - システム境界エラー（長文入力時の文字数上限超過による強制終了）
  - ガードレール失敗（危険なプロンプトに対するブロック漏れ）

## 改善

- 改善前：文字数上限（200文字）を超える入力で処理がクラッシュし、また危険な指示をそのまま受け入れてしまう状態だった。
- 改善後：文字数超過時は上限で安全に切り詰める処理を追加し、禁止ワードによるセキュリティガードを実装。自動評価基盤により、他の正常系をデグレードさせることなく修正できたことを実証した。

## 実行方法

### テスト入力セットの実行方法

```bash
# 基本的な実行
python -m day09.app --suite day09/suite.json

# 出力先を指定
python -m day09.app --suite day09/suite.json --out day09/result.json

# タイムアウトを指定
python -m day09.app --suite day09/suite.json --timeout-sec 60
```

### 結果の見方

- 標準出力：成功/失敗件数のサマリ
- `--out` で指定したファイル（デフォルト: `day09/result.json`）：詳細な結果JSON

```bash
# 結果ファイルを確認
cat day09/result.json | python -m json.tool
```

Windows（PowerShell）の場合：

```powershell
Get-Content day09\result.json | python -m json.tool
```

## リサーチメモ（任意）

調べたURLや、理解した要点をメモしてください。

- **自動評価基盤（評価ハーネス）の真の価値**
  AIエージェント開発では、プロンプトや分岐条件の微細な変更が、今まで動いていた別の正常な処理を壊してしまう「デグレード（副作用による品質低下）」が頻発する。都度手動でテストするのは非現実的であり、今回のようにコマンド一つでテストセットを一括実行し、合否を数値化（passed/failed）する仕組みこそが、実運用における品質担保の要であると腹落ちした。
- **「先祖返り」と「デグレード」の明確な違い**
  ファイルの古い状態に戻ってしまう「先祖返り」ではなく、ある弱点（例：プロンプトインジェクション）を修正した副作用で別機能（例：通常の要約）が壊れる「デグレード（リグレッション）」を検知することが、この自動評価の主目的であると理解できた。
- **テストケースの網羅的な設計**
  `suite.json` に、正常系だけでなく「空文字（異常系）」、「長文（境界値）」、「攻撃プロンプト（ガード）」を意図的に組み込むことで、システム全体の耐久性を測る健康診断として機能する。この評価基盤があることで、コード修正時の安心感が全く異なることを実感した。
