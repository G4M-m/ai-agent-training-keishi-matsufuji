# Day 03

## 受講者が実装する場所

- `day03/app.py` の `generate_json()`

## 目的

- LLM出力を構造化（JSON）し、後段処理しやすい形にする
- JSONが壊れたときに安全に復帰/失敗できるようにする

## ゴール（完了条件）

- 標準出力にJSONのみが出力される
- JSONが壊れた場合に `--max-retry` の範囲で復帰できる（または明示的に失敗できる）

## JSON仕様

例として、次のようなJSONを返すタスクにします（必要に応じて調整してOK）。

- `title`：依頼の要約タイトル
- `tasks`：タスク配列
  - `id`：連番
  - `description`：作業内容
  - `acceptance_criteria`：完了条件
- `risks`：想定リスク

## 機能要件

コマンド

- `python -m day03.app` で起動できること（モジュール名は固定）

必須オプション

- `--requirements`：要件（文字列、必須）

任意オプション

- `--max-retry`：JSON破損時の再生成回数（整数、デフォルト `1`、0〜3）

出力

- 正常時：標準出力にJSONのみを出力する（余計な説明文を混ぜない）
- 失敗時：標準エラーにエラーメッセージを出力する

終了コード

- 正常終了：`0`
- 入力不備（未指定、空など）：`2`
- JSON生成/検証に失敗：`1`

検証

- 生成された文字列をJSONとしてパースできること
- `title` / `tasks` / `risks` のキーが存在すること
- `tasks` は配列であること

フォールバック

- JSONのパース/検証に失敗した場合、`--max-retry` の回数だけ再生成する
- それでも失敗した場合は終了コード `1` で終了する

## 実装タスク

- `day03/app.py` の `generate_json()` を実装し、機能要件を満たす
- JSON仕様に沿ったキー/型を安定して生成できるようにする

## 実行方法

### 実行コマンド例

```bash
# 基本的な実行
python -m day03.app --requirements "ユーザー登録機能を作る"

# リトライ回数を増やす
python -m day03.app --requirements "ECサイトの購入フローを設計する" --max-retry 3
```

## セルフレビュー

- 正常系：短い要件（ユーザー登録機能）で、後続処理でパース可能なJSONが正しく返ることを確認した。
- 異常系：出力が途切れたり壊れたりした場合に、システムが暴走せず設定した上限回数でフォールバックが働くことを確認した。
- 境界：長めの要件（ECサイトの購入フロー）を入力した際、当初は出力が途切れてエラーになったが、設定をチューニングすることで大規模なJSONでも極端に崩れず出力できるようになった。
- 再実行：同じ入力で2回実行しても必須キー（title, tasks, risks）が欠けないことを確認した。

## フォールバック

- JSON破損時の挙動：`json.loads()` でのパースや必須キーの検証に失敗した場合、`main()` 関数内のループにより `--max-retry` で指定した回数分だけLLMへ再リクエストを試みる。今回の検証で発生した「文字数上限による出力途中でのぶつ切り（Unterminated stringエラー）」の際も、指定回数のリトライを実施した後、無限ループに陥ることなく安全にエラーログを吐いて終了コード `1` で処理を停止する（システム全体のクラッシュを防ぐ）挙動を確認できた。

## リサーチメモ（任意）

- **システム連携における出力固定の重要性：**
LLMの出力を後段のプログラムで処理（タスク管理ツールへの自動起票など）するためには、自然言語の回答ではなく、プログラムがピンポイントで値を抽出できるJSON等への構造化が必須となる。

- **揺らぎの排除とクレンジング：**
出力形式を安定させるため、プロンプトで「Markdownブロック等の余計な文字を含めない」よう強く指示し、Bedrock APIのパラメータで `temperature=0.0` を指定してランダム性を最小限に抑える設計とした。万が一の装飾混入に備えた文字列のストリップ処理（簡易クレンジング）も有効。

- **【重要】トークン上限によるJSON破損リスクの発見と対処：**
「ECサイトの購入フロー設計」という出力項目が多い要件をテストした際、`max_tokens=1024` の設定では出力途中で文字数制限に達してしまい、末尾の `}` が欠落してJSONパースエラーが発生した。`max_tokens` を `5000` に拡張することで解決したが、実務のシステム設計においても「LLM特有の文字数制限による構造破壊リスク」をあらかじめ想定し、適切なパラメータ設計とリトライ上限の設定を行っておくことが不可欠であると深く学んだ。
